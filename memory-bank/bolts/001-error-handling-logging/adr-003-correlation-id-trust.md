# ADR-003: Trust Client-Provided X-Correlation-Id (Validate, Don't Reject)

## Context

The `CorrelationIdMiddleware` must assign a correlation ID to every HTTP request for end-to-end log traceability. There are two strategies:

1. **Always generate**: Ignore any `X-Correlation-Id` header from the client; always create a fresh `Guid.NewGuid()`
2. **Accept if valid**: Read `X-Correlation-Id` from the request header; use it if it's a valid GUID, otherwise generate a new one

The Angular frontend (and any future upstream proxy or API gateway) may send a correlation ID to link its own log entries to backend log entries for the same user action. For example, the frontend might generate a correlation ID when a user clicks "Place Order" and include it in every API call made during that checkout sequence.

Security considerations:
- A malicious client could send a crafted correlation ID to attempt log injection
- A malicious client could send another user's correlation ID to confuse audit trails

## Decision

Accept a client-provided `X-Correlation-Id` header if and only if it is a valid UUID (parseable as `Guid` via `Guid.TryParse`). If the header is missing, empty, or not a valid GUID, silently generate a fresh `Guid.NewGuid()`. Never reject the request or return an error for an invalid correlation ID header.

## Rationale

Distributed tracing across the Angular frontend and the ASP.NET Core backend is a legitimate and valuable use case. If the frontend initiates a user action and assigns a correlation ID, having the same ID in both browser console logs and server logs makes debugging user-reported issues significantly faster.

The security concern (log injection) is mitigated by:
1. **Strict validation**: Only valid GUIDs are accepted — no free-form strings, no special characters
2. **Structured logging**: Serilog logs the correlation ID as a named property (`{CorrelationId}`), not as a string interpolated into a message template — this eliminates log injection entirely
3. **No trust escalation**: The correlation ID is purely a tracing label. It does not grant permissions, affect authorization, or alter business logic

Rejecting the request for an invalid ID would be overly strict and break legitimate clients that send malformed IDs (e.g., empty string from a misconfigured proxy).

### Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|--------------|
| Always generate, ignore client header | Zero trust, no security surface | Breaks distributed tracing; frontend and backend logs cannot be correlated | Rejected — loses significant operational observability value |
| Accept any non-empty string | Maximum tracing flexibility | Log injection risk if Serilog ever logs via message interpolation; pollutes logs with arbitrary values | Rejected — unnecessarily broad trust; GUID constraint is sufficient |
| Accept and cryptographically verify (signed ID) | Strongest security | Major complexity; requires shared key between frontend and backend | Rejected — over-engineering for correlation ID whose only purpose is log tracing |
| Return 400 for invalid GUID header | Forces clients to send valid IDs | Breaks requests from proxies or clients sending legacy/empty correlation headers | Rejected — correlation ID is a tracing concern, not a validation concern |

## Consequences

### Positive

- Frontend-backend distributed tracing is possible without additional infrastructure
- Valid correlation IDs from upstream proxies (Nginx, API gateway) are preserved
- Silent fallback (generate fresh ID) means no client requests are ever rejected for this header

### Negative

- Backend logs may contain correlation IDs not generated by the backend — this is intentional but must be understood by operators
- Serilog's structured logging discipline must be maintained; if a developer ever logs `correlationId` via string interpolation (not structured), the injection risk re-emerges

### Risks

- **Risk**: Future developer changes Serilog logging to use string interpolation with `correlationId`, enabling log injection. **Mitigation**: Coding standards require structured logging (`Log.Information("Processing {CorrelationId}", id)` not `Log.Information($"Processing {id}")`); enforced in code review.
